Sources

Bring in the configuration and the usage statistics the assessment runs on. Collect straight from the device, or import files on an air-gapped network — the analysis is identical.

Collect from device instead of uploading files (optional)

Connect to a FortiGate over its REST API and pull the configuration, hit-count / last-used stats, and FQDN resolutions in one step — no file exports needed. A read-only API token is enough (this only reads; it never changes the device). Prefer the file-upload path on air-gapped networks. The token is kept in memory only, never written to disk.

Unreachable
Unreachable Policy Detection

          
        

        
A policy is listed here only when a single always-on policy above it provably matches every packet it could match (source, destination, service, and interfaces all contained) — so it never takes effect. Conservative static analysis: policies using geography / ISDB / user objects or negation are skipped, not guessed. Routing and NAT are not considered.

        

          
          
          
          If you collected from the device, FQDN resolutions are already included. Otherwise fetch them from a connected device, or upload the output of diagnose test application dnsproxy 6. Either way the results are re-classified automatically and marked "DNS capture" (provable as of capture time).

Evidence

        
The record a reviewer or auditor asks for: what was reviewed and when, and a way to
           measure how accurate these judgements actually are on your firewall.

      


      

        

          
Audit Trail
Ruleset Review Evidence

          PCI-DSS v4.0 Req 1.2.7 — review NSC configurations at least every six months
        

        
Upload two or more config snapshots (oldest first — FortiGate configs carry no backup timestamp, so the order you provide is the order recorded). APO builds a change timeline between snapshots and exports a Review Evidence workbook: each snapshot's SHA-256, changes per interval, the PCI-DSS citation, and a reviewer sign-off block. Collect snapshots with whatever you already use — Oxidized, FortiManager revisions, manual backups.

Verify
Accuracy Verification

          Free — verify APO's calls against your firewall before you trust them
        

        
Don't take this report on faith. APO draws a stratified sample across severity levels (up to ~31 policies), each with what to check and the exact CLI commands to run on your FortiGate. Fill in what you actually found and whether the call matched, then upload the sheet back — APO computes per-level precision. Held or unfilled rows are excluded from the denominator, never counted as right or wrong.

How policies are judged

        
The criteria behind every severity and action in this tool. Nothing here is
           configurable — adjust the numbers under Settings.

Severity Classification Criteria

        

        

          

            
              
SeverityRisk LevelActionClassification CriteriaNotes

            
            
              

                7
                None
                Keep
                ① Action = Deny
② ICMP-only service (Ping, etc.)
③ Valid change ticket (ticket ID present + schedule not expired)
④ Policy name contains "controlled" (multi-firewall passthrough)
⑤ Policy matches a configured admin object and carries no risky service		
                Two different meanings share this rating — see the Action column. No risk means assessed and found fine (deny, ICMP-only). Not assessed (exempted) means an exception rule stopped the assessment; it does not mean the policy is safe. An admin policy that still permits a risky service is rated 3, not 7
              

              

                1
                Critical
                Disable now
                ① Source, destination, and service are all Any/All
② Source or destination Any/All + Hit Count = 0
③ Source or destination Any/All + Hit Count > 0 but Last Used ≥ 1 year
④ Risky service only (FTP, TELNET, TFTP, RLOGIN, RSH)
⑤ Risky + normal service mixed + Hit Count = 0 or Last Used ≥ 1 year
⑥ Temp keyword in name (temp, etc.) + no ticket ID + Hit Count = 0
⑦ Service ALL + Hit Count = 0 or Last Used ≥ 1 year		
                Disable, then monitor 30–90 days before removing
              

              

                2
                High
                Review candidate
                ① Status = Disabled
② Schedule expired (YYMMDD date is in the past)
③ Hit=0 + Accept + Server↔User + registered ≥ 1 year ago
④ Hit=0 + Accept + Server - Server + always schedule + > 1 year		
                Confirm with the policy owner before removing. Already-disabled and expired policies are removal candidates; live but unused policies should be disabled and observed first
              

              

                3
                Medium
                Additional Review Required
                ① Server - User + registered > 1 year + Hit < elapsed years×100 + Last Used ≥ 1 year
② Risky + normal service mixed + actively used (within 1 year)
③ Source/Destination Any·All + active use (within 1yr) + Server - User
④ Service ALL + active use (within 1yr) + Server - User		
                ② Mixed risky policy: do NOT delete the entire rule — remove only the risky service/port, keep normal services
              

              

                4
                Medium
                Additional Review Required
                ① Server - Server + registered > 2 years + Hit < 50
② Server - Server + registration date unknown
③ Source/Destination Any·All + active use (within 1yr) + Server - Server
④ Service ALL + active use (within 1yr) + Server - Server		
                For active Any/All policies, recommend narrowing scope instead of immediate disable
              

              

                5
                Low
                Register ticket
                ① Server - User + registered < 1 year + no ticket ID
② Server - User + registered > 1 year + insufficient hits + Last Used < 1 year (recently active but not formally registered)
③ Service ALL + active use (within 1yr) + Server - User		
                Keep the policy, but raise a change ticket so the access has an approval record
              

              

                6
                Low
                Register ticket
                ① AD/DNS/LDAP authentication service + Hit > 0
② Server - Server + within 2 years + no ticket ID
③ Server - Server + Hit ≥ 50
④ A configured infrastructure or management object is included		
                Keep the policy, but raise a change ticket so the access has an approval record
